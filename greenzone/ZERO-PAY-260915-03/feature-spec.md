## 1. 목적

`TB_QR_MNG.ZERO_AMT_SETL_YN` (0원결제여부) 플래그가 **채널마다 반대 의미로 동작**하고 있어 정합화한다.

- 플래그의 확정 의미 = **「잔여한도가 0이어도 결제를 허용한다」** (`BPPG_100001_act.jsp:783` 이 플래그 N + `usableMealLmt==0` 이면 `E004 이용가능한 한도가 없습니다` 로 차단하는 것이 근거). 「한도가 남아도 식권을 0으로 만들라」가 아니다.
- **결함 1 (키오스크)** — 승인 단계 `BPPG_100002_act.jsp:692-699` 가 잔여한도를 읽지 않고 `mealTrxAmt = 0` 으로 덮어써, 잔여 마일리지가 있어도 식권 0원 · 비플머니 전액으로 승인된다. 결제준비(`BPPG_100001:1321-1323`)는 이미 `usableMealLmt > 0 || isZeroMealTran` 라 수정 대상이 아니다.
- **결함 2 (앱 내 결제)** — 같은 플래그를 `WALT_000005_act.jsp:315`·`COIN_000005_act.jsp:314` 는 `throw 312 "0원 식권 결제 불가"` 로 거부한다. 동일 구조의 `ZERO_000005_act.jsp:313-316` 은 2026-06-09(김재경) 주석 처리로 이미 해제되어 운영 중이므로, 같은 플래그가 형제 파일 사이에서 반대로 동작한다.

목표는 **세 채널의 동작 결과를 일치**시키는 것이다. 채널별 금액 분할 **주체**가 서로 달라(키오스크·제로페이 = 서버가 한도로 계산 / 스마트오더 `bp_order_pay_c001` = 화면이 `MEAL_TRX_AMT`·`MNY_TRX_AMT` 를 전달) 로직 통일은 구조상 불가하며, 범위는 **동작 결과 일치**까지다.

## 5. 보안 고려사항

- 개인정보·인증정보 신규 노출 **없음** — 회원코드(`MEMB_CD`)·계좌번호는 기존 로그 라인 그대로이며 신규 로그를 추가하지 않는다.
- 금액 계산 변경이므로 **금액 조작 가능 입력이 늘지 않는지** 확인이 필요하다. 교정 후 식권 차감액의 상한은 서버가 산출한 `usableMealLmt` 이며 **클라이언트 입력이 아니다** — 클라이언트가 식권 몫을 지정할 수 있는 경로는 생기지 않는다.
- 요구 03(한도검증 가드 조정)은 **검증을 여는 방향**이다 — 종전에 검증을 건너뛰던 건이 1회·일·월 한도검증을 지나게 되므로 보안·통제 관점에서 완화가 아니라 강화다.
- 시크릿·DB 접속정보 취급 없음. JexStudio MCP 호출 없음.

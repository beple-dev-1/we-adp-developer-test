## 1. 5분 안에 돌려보기

```bash
git clone https://github.com/beple-dev-1/we-adp-developer-test
cd we-adp-developer-test

node scripts/selftest.cjs     # 회귀 테스트 — 하네스 없어도 돈다
node scripts/task-ledger.cjs --root {하네스경로} --group BIZ_ZEROPAY   # ★ 먼저 원장을 만든다
node scripts/serve.cjs        # → http://localhost:8080/developer.html
```

**`web/ledger.json` 은 레포에 담기지 않는다.** 사람마다 자기 하네스의 과업을 봐야 하는데,
커밋하면 pull 한 사람이 **만든 사람의 과업**을 보게 되고 각자 재생성분을 커밋하면 서로
덮어쓴다. 그래서 각자 만든다 — 하네스가 없으면 화면이 "원장을 아직 만들지 않았습니다"
안내를 띄운다(보기 전용도 안 된다).

`developer.html` 을 **더블클릭하면 화면이 빈다.** 브라우저가 `file://` 에서 `ledger.json` 의
`fetch` 를 막기 때문이고 파일이 깨진 게 아니다. 반드시 `serve.cjs` 로 띄운다.

### 데이터를 새로 만들려면 — JEX 하네스가 있어야 한다

```bash
node scripts/task-ledger.cjs --root {하네스경로} --group BIZ_ZEROPAY   # → web/ledger.json
node scripts/greenzone.cjs  build --root {하네스경로} --group BIZ_ZEROPAY
```

하네스가 없으면 `exit 2` 로 **명확히 멈춘다**(추측해서 엉뚱한 원장을 만들지 않는다).

### 받아서 열면 무엇이 되나

| 항목 | 하네스 있음 | 하네스 없음 |
|---|---|---|
| 회귀 테스트 (`selftest.cjs`) | 된다 | **된다** |
| 화면 뜨기 (`serve.cjs`) | 된다 | **된다** (데이터는 빈 안내) |
| 원장 생성 → **자기 과업** 보기 | **된다** | 안 된다 |
| 기능명세서 생성 | 된다 | 안 된다 |
| 그린존 산출물 보기 | 된다 | **된다** (레포에 담김) |

**하네스가 있으면 `--root` 만 주면 자기 과업이 나온다** — 그것이 의도한 결과다.
원장을 레포에 담지 않는 이유가 바로 이것이다.

## 2. 이 시스템이 무엇인가

WE-ADP 4단위시스템(Planner · Builder · **Developer** · Admin) 중 Developer 의 비플페이 구현.

```
Builder ──push──▶ 저장소 레포 ──clone/fetch──▶ Developer ──개발──▶ 그린존 반환
                                            │
                                   하네스 target/tasks/ 스캔
                                            ▼
                                      ledger.json ──▶ 화면
```

### 설계에서 물러서지 않은 것 — 고치기 전에 읽을 것

1. **사람이 상태를 입력하는 곳이 없다.** 개발자가 평소처럼 `/dev-plan`·`/qa-test`·`/code-review`
   를 돌리면 산출물 파일이 생기고 **그 파일의 실재가 곧 상태**다. 상태 입력란을 만들면
   반드시 빠지고, 빠진 채로 "최신"처럼 보인다.
2. **유도할 수 없으면 추정하지 않는다.** 추정한 값은 `statusInferred:true` 와 `statusVia` 로
   출처를 데이터에 싣고 화면도 "그중 추정 N" 으로 드러낸다.
3. **한계표를 지우지 않는다**(`docs/task-ledger.md`). 빼고 "잘 동작함"만 남기면 다음 사람이
   추정 판정을 사실로 믿는다.
4. **발행 게이트에 우회 인자를 만들지 않는다.** 예외가 없다는 것이 그 게이트의 값이다.

| 기준 | 무엇을 가져왔나 | 주의 |

### 컨셉 목업이 적대검증으로 잡아 둔 함정 (그대로 따랐다)

```css
.pop__body a.notice--read,
.notice--read { color: var(--color-muted); }
```

`.pop__body a`(특이도 0-1-1)가 생기면 `.notice--read`(0-1-0)가 색을 못 이겨 **읽음 표시가
조용히 사라진다.** 선택자를 단순화하지 말 것. `selftest.cjs` 가 이걸 지킨다.

## 5. 판정 규칙 — 숫자가 어디서 오나

### 과업 상태 4택 (접수 · 개발중 · 리뷰중 · 완료)

진입 단계별로 어떤 산출물이 있으면 어느 상태인지가 정해져 있다(`task-ledger.cjs` `ENTRY_PATHS`).
`investigate`/`ops`/`harness` 는 완료 표시를 남기지 않으므로 **산출물 존재** 또는 **14일 무변경**
으로 완료를 보되 `statusInferred:true` 를 붙인다.

### TRD 는 언제 생기나

TRD = 계획서의 **페이즈 문서**(`plan/phases/phase_N.md`)다. 아래를 거쳐야 생긴다.

```bash
# ①채번 ②연결 ③원장재생성 을 한 번에 — 기본은 미리보기, --yes 로 실행
node scripts/intake.cjs --request REQ-BPL-0001 --entry=plan --root {하네스} --yes

/dev-interview {과업번호}     # entry=interview 일 때만
/dev-plan {과업번호}          # ★ 여기서 TRD 가 생긴다
```

`intake.cjs` 가 하는 일 — 요청서를 읽고 도메인을 판정해 채번하고, 요청서 JSON 의
`linkedTaskIds` 에 되쓰고, 원장을 다시 만든다. 손으로 JSON 을 고치던 자리를 없앤다.

- **기본은 미리보기다.** 채번은 과업 폴더·세션 상태를 만들어 되돌리기가 번거롭다.
- **`--entry` 에 기본값이 없다.** entry 가 TRD 유무를 가르는데 기본값을 두면 그 선택이
  조용히 일어난다.
- **도메인 후보가 여러 개면 과업을 나눈다.** 실측 — "바코드 결제토큰 체크디지트 검증 강화"
  는 `code_master`·`payment`·`money` 3개가 같은 점수다. 하나를 임의로 고르면 지식 로딩과
  TC 도메인코드가 오염되므로, 도메인마다 하위 과업을 만들고 요청서에 전부 잇는다.
  한 도메인으로 묶으려면 `--domain={id}` 로 지정한다.
- 이미 과업이 연결된 요청서는 **거부**한다(중복 채번 방지).

**`--entry` 가 TRD 유무를 가른다.** `interview`·`plan` 만 계획서를 만들고,
`direct`·`investigate`·`ops`·`harness` 는 계획서가 없어 **TRD 가 영영 안 생긴다**.
실측 — BIZ_ZEROPAY 21건 중 `plan` 5 · `direct` 8 · `investigate` 7 · `ops` 1.
계획서 36건 중 33건이 페이즈를 가진다(나머지 3건은 단일 작업).

세부 업무 내용 화면이 **지금 어느 단계인지에 맞춰 이 명령을 보여 준다.**
화면은 실행하지 않는다 — 터미널에서 친 뒤 원장을 다시 만들면 반영된다.

### TRD 상태 — ⚠ 지금은 유도값이다

TRD = 계획서의 페이즈 문서다. 페이즈 문서에 **기계가 읽을 완료 표시가 없어**(실측 84건)
과업 상태에서 유도한다. 그래서 **한 과업의 TRD 가 전부 같은 상태로 보인다.**
→ 페이즈 문서에 완료 플래그를 넣는 것이 **개선 1순위**다.

### 담당자

`target/assignments.json`(하네스) 하나가 유일한 지정 자리다. 원장은 매번 새로 만들어
사람이 누른 값을 담을 수 없다.

```json
{ "default": "비플개발센터", "tasks": { "ZERO-PAY-260914-03": "최재혁" } }
```

파일이 없으면 `git config user.name`(= 원장 만든 사람)으로 떨어지고, **그것이 수행자가
아니라는 사실을 `ownerVia` 로 데이터에 싣는다.** 화면 안내문도 그에 따라 바뀐다.

### system → 작업그룹 매핑

저장소 레포에는 그룹 축이 없다(`BIZ_ZEROPAY` 문자열 0건). 근거 있는 것만 적었다.

| system | label | 그룹 | 근거 |
|---|---|---|---|
| `EXW` | 외부제공 웹뷰 | `BIZ_ZEROPAY` | 명세가 지목한 `brnd_webview_gift_list_view.jsp` 가 실제로 그 프로젝트에 있음(대조 완료) |
| `BPY` · `HIT` | 비플페이 앱 · 힛플러스 | `BIZ_ZEROPAY` | 사용자 확정 |
| `MCH` | 가맹점관리 | `AFLT` | 사용자 확정 |
| `BPG` | 비플PG | `BPPAY_PG` | manifest label (소스 대조는 안 함) |
| `MGC` | 모바일상품권 | — | **미정** |

## 6. 성능 — 왜 이렇게 부르나

과업마다 `node task-paths.cjs` 를 spawn 하던 것을 한 프로세스로 모았다.
비용의 90%가 **node 기동**이었다(실측: 빈 node 370ms · 실제 일 36ms).

| | 전 | 후 |
|---|---|---|
| BIZ_ZEROPAY 21건 | 5,264ms | 891ms |
| BPPAY_PG 88건 | 24,028ms | 1,174ms |
| 전체 181건 | 49,164ms | 611ms |

**경로 정본은 여전히 하네스의 `task-paths.cjs` 이고 하네스는 한 줄도 고치지 않았다.**
다만 그것이 *main 가드 없는 순수 CLI* 라는 구조에 기댄다 — 그래서 `selfCheck()` 가 spawn
1회와 대조해 어긋나면 느린 길로 되돌아가고 경고를 남긴다. **조용히 틀리느니 느린 게 낫다.**

## 7. 고칠 때 지킬 것

1. **`scripts/selftest.cjs` 를 먼저 돌린다.** 68건이 컨셉 규격·CSS 특이도·폭 상한·경로 스크럽
   같은 "조용히 사라지는 것"을 지킨다. CI(`.github/workflows/selftest.yml`)도 같은 걸 돈다.
2. **스키마를 바꾸면 화면의 `ACCEPTED_SCHEMA` 도 올린다.** 안 올리면 화면이 데이터를 안 그린다
   (selftest 가 잡는다).
3. **원장에 파일 경로·이메일을 싣지 않는다.** `scrub()` 이 지우고 스키마가 한 번 더 막는다.
4. **어댑터 폴더는 신뢰 경계다** — 놓인 `.cjs` 가 `require` 로 그대로 실행된다.
5. **정규식·이스케이프가 들어가는 편집은 편집 도구로 한다.** bash heredoc + python 경로는
   백슬래시를 한 겹 먹어 정규식을 조용히 깨뜨린다(이 세션에서 4번 밟았다).

## 9-1. 개발요청서(DR) 회신 규격 — 실측 2026-09-26

`scripts/greenzone-return.cjs` 가 다루는 것. **기능명세서(그린존)와 다른 산출물**이다 —
저쪽은 우리가 만든 것을 열람 구역에 내는 것이고, 이쪽은 요청마다 정해진 자리에 정해진
파일을 돌려주는 것이다.

| 무엇 | 어디 |
|---|---|
| **규격 정본** | `{DR}/manifest.json` 의 `expectedBack` — `returnBranch`·`base`·`screens[].required[]`·`tests.{unit,integration}[]` |
| 사람용 사본 | `{DR}/expected-back.md` (v2). **v3 는 껍데기다** — "Developer 는 이 파일을 받지 않는다(스펙 4-4)" |
| TC 원본 | v2 `expected-back.md` 의 9칸 표 · v3 `{DR}/test-cases.md` 의 3칸 표 |
| 받는 쪽 규약 | 저장소 레포 `dev-requests` 브랜치의 `README.md`·`TESTING.md` |

**밟기 쉬운 것 4가지**

1. **반환 브랜치를 조립하지 마라.** v2 는 `feedback/{시스템}/{DR}`, v3 는 `feedback/{DR}` 로
   **시스템 마디가 빠졌다.** `'feedback/' + system + '/' + dr` 로 짜면 v3 에서 틀린 브랜치에
   올라간다 — 거절이 아니라 **엉뚱한 곳에 올라간 것**이라 아무도 모른다. selftest 가 막는다.
2. **전달 브랜치(`dr/…`) 위에서 따지 마라.** 거기엔 기획이 그린 to-be 가 있어 그것이
   *사실인 척* 섞여 들어가고, Builder 는 「기준이 기본 브랜치 이력에 없습니다」로 통째로 거절한다.
3. **TC 번호 공간이 둘이다.** 하네스는 `TC-{과업번호}-017`, Builder 는 `TC-001` 이고 둘을 잇는
   근거가 없다. 그래서 판정 칸을 자동으로 채우지 않는다 — 빈칸으로 내고 `check` 가 막는다.
   **보낸 적 없는 TC 를 더하면 통째로 거절**된다.
4. **표는 9칸 고정.** 칸을 빼거나 합치면 그 줄을 못 읽는다. 셀 안의 `|` 는 `\|` 로 적는다.

**`check` 가 올리기 전에 재현하는 거절 사유** — 기준 커밋이 기본 브랜치 이력에 없음 ·
화면 집합 불일치(빠짐·없는 화면) · 필수 구성요소 누락 · 모르는 상태값 · 적은 상태와 실제
차이 불일치 · 갈라 온 뒤 기본 브랜치가 그 파일을 고침 · 보낸 적 없는 TC · 9칸 아님 ·
판정 공란·허용 어휘 위반.

> 실측 대조 — DR-015 는 이미 `main` 에 머지돼 있어, 그 `base` 로 지금 회신을 만들면
> `check` 가 "갈라 온 뒤 기본 브랜치에서 이 파일이 바뀌었다" 로 막는다. 게이트가 실제
> 이력에서 작동하는 것을 확인한 자리다.
